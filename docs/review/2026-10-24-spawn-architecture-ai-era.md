# Spawn 架构审核：AI 编码时代的框架与服务边界

日期：2026-10-24。审核基线：`f9b923e77b04c29aba734f63f9c0228c970618d2`。本文只记录审核与建议，不实施架构迁移。

## 结论

**保留 go-zero，采用折中策略：保留现有 HTTP 运行时，缩小生成器管理范围，业务代码由人和 LLM 维护；不做全仓迁出。** 当前有真实的多进程、领域数据隔离和失败降级，判定为**早期微服务，尚未形成成熟的独立交付体系；证据不足以判为分布式单体**。优先处理数据持久化、生产配置和契约漂移，而非更换框架。依据分别见 `services/user-service/user.go:38`、`services/api-gateway/internal/handler/routes.go:1`、`docker-compose.yaml:33`、`services/content-service/internal/logic/createguidelogic.go:50`，以及下文逐项证据。

本次给出 **14 个改进方向：P0 3 项、P1 7 项、P2 4 项**。工作量为一名熟悉 Go/本仓库工程师的有效人日估算，含实现与针对性验证，不是实测工期；不含等待部署窗口、数据量相关的迁移耗时。估算均以所列代码影响面为依据。

## 审核方法与证据边界

- 实际目录叫 `services/`，不是 `service/`；八个模块由 `go.work:3` 至 `go.work:12` 明确列出。阅读八个 main、装配层、路由、关键逻辑、数据模型、配置、Dockerfile、Compose 和 CI，而不以 README 的功能宣称代替实现。
- 下文 `file:line` 为上述基线的仓库相对路径和起始行；区间需要时用多处锚点表示。事实、风险推断与建议明确区分。对不存在的能力，以限定范围的检索事实及对应配置/入口证据说明，不能给不存在的文件编造行号。
- 对 `services/**/*.go` 逐文件统计：378 个 Go 文件，其中 225 个非测试文件、153 个 `_test.go`，非测试代码 18,339 行（含注释及生成文件）；156 个非测试文件直接引用 go-zero，12 个文件带 `Code generated by`，83 个带 `Code scaffolded by`。这是工作树扫描事实，不等于测试覆盖率或待重写代码量。可复核：Python `Path('services').rglob('*.go')`，按文件名后缀分组，以 `splitlines()` 计行，以文件内容统计上述字符串。
- 对 `services/` 的非测试 Go 源码跨服务 module import 检索未发现业务服务直接导入另一服务的实现；对 Go 源码和 go.mod 检索 `sqlx|sqlc|gorm|kafka|amqp|nats` 未命中。这不证明仓外生产部署不存在相关设施。
- 本次为静态审核，没有启动 Compose、访问生产库或执行全套 Go 测试；CI 配置和已有测试只能证明存在验证机制，不能冒充本次测试通过。流量、团队人数、生产拓扑和发布频率未知，规模判断基于当前实现而非假定 DAU。

## 一、go-zero 是否应当迁出

### 先校正前提

`go get` 管依赖，不是本仓的代码生成命令。仓库明确使用 `goctl api go` / `goctl rpc protoc`，见 `README.zh.md:90`、`README.zh.md:92`；运行时直接使用 `rest.MustNewServer`、`httpx.SetErrorHandlerCtx` 和配置加载，见 `services/user-service/user.go:38`、`services/user-service/user.go:42`、`services/user-service/user.go:46`。所以 go-zero 同时是运行时依赖与生成工具生态，LLM 能写样板代码并不自动替代运行时行为。

官方资料交叉核实：[goctl CLI](https://go-zero.dev/reference/cli-guide/) 明确将 goctl 定义为生成工具；[安装与入门](https://go-zero.dev/getting-started/) 使用 `go install` 安装。外部资料只用于术语核实，项目判断以下列仓内证据为准。

### 收益与代价逐项对比

| “AI 不熟黑话” | `svc`、`logic`、`RestConf` 和 `httpx` 的具体关系可从 `services/user-service/user.go:38`、`:48`、`:52` 跟到；命名却混用 `servicecontext.go` 与 `service_context.go`（`services/community/internal/svc/service_context.go:26`） | 无模型成功率实验，不能断言 AI 不熟框架；可证实的是跨目录定位成本。增加服务地图、术语映射、改端点示例、生成边界说明，以少量文档降低猜测。 |

| 可靠性能力是否全来自框架 | 内容客户端自行实现重试/熔断（`services/content-service/client/gamecatalog.go:118`），BFF 自行并发/降级（`services/api-gateway/internal/logic/homefeedlogic.go:60`、`:67`），日志/指标配置依赖现有服务装配（`services/api-gateway/etc/gateway-api.yaml:36`） | 不能宣传框架自动解决所有微服务问题，也不能认为换成 net/http 就无成本。迁移需要逐项保留行为；优先统一现有实现的超时与错误契约。 |

### 三种策略与迁移成本

| 策略 | 具体范围 | 粗工作量与风险 | 决定依据 |
| --- | --- | --- | --- |
| 原样全保留 | 继续 `@latest` 工具、现有路由/契约混合维护 | 初始 0 人日，后续漂移风险持续；`gateway.api:113` 与生成路由混写就是反例 | 不选；证据为完整路径 `services/api-gateway/gateway.api:113`、`services/api-gateway/internal/handler/routes.go:41` |
| 折中保留（选定） | 锁工具、明确机械生成边界、分离自定义路由、补契约校验，保留六个 REST 服务与 stdlib hub | 约 8–15 人日完成首轮治理；不改业务数据和对外 URL，无数据库迁移。先做 gateway 试点再复制，仍需验证解析、鉴权与错误响应 | `services/api-gateway/gateway.go:48` 至 `:54` 已支持独立注册扩展；仓储接口可保持不动（`services/user-service/model/usermodel.go:39`） |
| 全迁出 go-zero | 替换六个 REST 服务的路由、解析、配置、错误处理、日志/指标装配与相应测试；RPC 骨架归档或另用 grpc-go | 约 30–60 人日（6–12 人周），按六个 REST 服务每个 3–6 人日，加公共适配、联调与回滚 12–24 人日估算；保留 DB schema/HTTP 契约时本身无数据搬迁。hub 已无此迁出负担 | 156 个直接依赖文件的扫描规模；`services/user-service/user.go:38`、`:42`、`:46`、`:52` 显示不止换 import；`services/api-gateway/internal/handler/routes_integration_test.go:24` 显示测试也绑定运行时 |

未来只有在具体特性持续受框架阻碍、维护成本试点证明确实下降时再迁；用 data-panel 四个端点作为 3–5 人日对照试点，而不是先迁最大 community。端点规模见 `services/data-panel/internal/handler/routes.go:15`、`:38`。此估算包含在全迁出范围内，不应重复相加。

### 数据面：有库隔离，不等于已生产化

默认 Compose 下五个数据域各有 SQLite 文件，user 由 Compose 覆盖，其余由配置/Dockerfile 默认指定；证据见上表及 `services/game-catalog/Dockerfile:18`。没有发现跨域 SQL join 或共享业务表访问；community 内多个 Repo 使用同一库是领域内共享，不是跨服务共享库（`services/community/internal/svc/service_context.go:91`、`:114`）。

必须区分三种情况：user 裸跑 YAML 默认连接 MySQL `tappi` 库（`services/user-service/etc/user-api.yaml:7`）；Compose 切到 users.db（`docker-compose.yaml:57`）；生产可另行传 DSN，实际是否独立 MySQL 实例/账号，仓库无法确认。其他服务也按 DSN 选择 SQLite/MySQL（例如 `services/content-service/internal/svc/servicecontext.go:35`）。**可确认逻辑数据所有权，不能确认生产物理隔离。**

当前默认 Compose 只给 uploads 挂卷（`docker-compose.yaml:19`、`:127`），五个数据库容器没有 data volume。容器重建可能丢失新增数据，普通进程重启则不能等同于重建；user 镜像还复制 test.db（`services/user-service/Dockerfile:16`）。启动时自动建表/seed（`services/game-catalog/internal/svc/servicecontext.go:51`、`services/data-panel/internal/svc/service_context.go:57`）不能替代 schema 版本迁移与备份恢复流程。

域间身份依赖是共享 JWT 密钥与 ID，而非共用用户表（`docker-compose.yaml:87`、`:98`；私信明确不查收件人存在性，`services/community/internal/logic/message/send_direct_message_logic.go:37`）。这降低同步耦合，却留下用户删除/禁用、名称快照和无效 ID 的一致性政策缺口；它们需要明确契约，不能靠强制所有服务查询用户库来解决。

### 真微服务还是分布式单体

判定标准是独立进程、领域数据归属、是否必须锁步发布、上游失败是否整体瘫痪；不是用了多少框架或有没有 K8s。

| 维度 | 判定 | 证据 |
| --- | --- | --- |
| 进程/构建隔离 | 成立：七个活跃后端独立容器，另有 RPC 骨架 | `docker-compose.yaml:4`、`:33`、`:41`、`:53`、`:68`、`:83`、`:94` |
| 数据所有权 | 默认成立：五个域独立文件；生产账号/实例隔离未验证 | `docker-compose.yaml:57`，四个领域 YAML 的 DataSource 见服务表 |

因此是**真实拆分的早期微服务，附带运维与契约欠账**，而不是有证据支持的分布式单体。共享签名密钥、同步 HTTP、同仓构建是耦合点，却不能单独推出“必须全体同启同停同发布”。现有软依赖是反证；未来若新增跨域写事务与锁步契约变更而不治理，才会趋向分布式单体。

### 规模匹配：哪里拆多了、哪里仍需分层

- **已有过度建设：RPC 空骨架。** 唯一方法还留 TODO（`services/user-service-rpc/internal/logic/pinglogic.go:27`），却进入全模块 CI（`go.work:11`、`.github/workflows/ci.yml:60`）；应归档或标成实验，不再为其上 etcd/部署资源。
- **data-panel 是偏细的独立进程。** 当前仅四个端点、一个 Repo（`services/data-panel/internal/handler/routes.go:15`、`:38`；`services/data-panel/internal/svc/service_context.go:28`）。没有独立团队/负载证据时暂停继续拆分；若维护成本占主导，可评估以独立模块并入业务宿主。不要为减少一个容器立即做数据库合并。
- **保留 hub 独立是合理的。** WS 长连接、Redis relay、webhook 与 CRUD 生命周期不同（`services/realtime-hub/realtime-hub.go:40`、`:45`、`:53`、`:56`），已有明确技术边界。
- **community 需要内部模块边界，而非立刻再拆进程。** 七个 Repo、审核配置、实时投递集中在一个 ServiceContext（`services/community/internal/svc/service_context.go:26`）；先把消息/审核用例依赖收窄。仅凭 6,285 行非测试代码的扫描结果不能宣称已必须拆成七个微服务。
- **content/community 的评论并不自动属于重复服务。** 前者围绕攻略收藏（`services/content-service/internal/svc/servicecontext.go:22`），后者围绕帖子社交（`services/community/internal/svc/service_context.go:31`）；保留领域归属，抽取少量鉴权/错误约定，不抽出跨域“万能评论服务”。
- **规模证据偏向小型实现。** 游戏模型明确按数百行目录全量读再排序（`services/game-catalog/model/gamemodel.go:55`），默认 SQLite 和自动 seed 也支持演示/早期阶段判断；不足以推定真实用户数。当前应减少运维负担、停止新增空服务，不应凭“AI 写代码便宜”继续增加部署单元。
