# 手游平台功能调研与 Spawn 扩展计划

调研日期：2026-10-29。范围：国内手游发现、社区、分发、联运及平台技术产品；同时核对本地 Spawn 与 Courier 的实现。本文是功能调研和需求整理，不代表下列待办已经实现或已通过上线验收。实施清单见仓库根目录 [todo.md](https://github.com/cuihairu/spawn/blob/main/todo.md)（本地以当前工作树为准）。

## 1. 已确定的产品约定

- 在 Spawn 上扩展，继续使用统一游戏库、账号入口和社区，不另建游戏平台项目。
- 联运游戏打上“联运”标签，沿用标签展示和筛选；不另设联运游戏库、独立游戏类型或社区/联运两种运行模式。
- 标签是展示信息。SDK、支付、下载等实际接入参数和权限单独配置，不能靠增加标签自动开通收款或下载。
- 倍率充值属于活动规则，与首充、累充、限时赠送等一起管理，不作为平台定位或游戏基础倍率字段。
- 游戏 SDK 复用现有 Courier 项目。Spawn 管平台业务和运营界面，Courier 管游戏内 SDK 与玩家能力契约，两者保留独立仓库和发布周期。
- 本轮只补调研与待办；阶段顺序是建议执行顺序，不是工期承诺。Android 下载链路优先，沿用既有移动端计划中 iOS/鸿蒙的低优先级安排。

## 4. Courier 复用核查

本地项目：`/home/cui/workspaces/courier`；[公开仓库](https://github.com/cuihairu/courier)。以下结论来自契约、装配和源码阅读，未在本轮重新运行六端或真实渠道测试。

| 能力 | 已找到的实现/证据 | 对 Spawn 的含义与未完成边界 |
| --- | --- | --- |
| 多引擎 SDK | `sdks/unity`、`ue`、`cocos`、`miniprogram`、`laybox`、`godot` | 不新建 Spawn SDK；UE 当前为无引擎 C++ 核心，不等于完整 UE 插件；RN 盒子也不能直接当 Unity 适配器使用 |
| 身份与会话 | `gateway/providers/account/`、`docs/zh/contract/scope.md` | 公司级 account 可复用，游戏会话按 game_id + env 隔离；Spawn JWT 不能直接用作 Courier 游戏会话 |
| 玩家角色 | `gateway/providers/archivist/archivist.go` | 已有按 scope 的账号↔角色映射，不代表已覆盖联运的区服、等级、职业、充值目标和全部运营事件 |

| 运营边界 | `README.zh.md` 设计边界 | Courier 面向玩家，不负责平台运营界面与联运渠道聚合；这些归 Spawn 平台侧及其适配组件 |

### 接入前必须写清的边界

1. **账号归属**：现有两套账号不能假设同 UID/同密码/互认 JWT。明确权威账号源、存量绑定与迁移方式；若需要单点登录，单独评估短期票据或 token exchange，不能绕过 Courier scope 校验。
2. **目录映射**：建立 Spawn game ID 与 Courier game_id/env 的配置映射。scope 只按 Courier 契约走 header；不向 URL/payload 塞隔离字段。
3. **交易唯一事实源**：确定由所选 PaymentsProvider 或外接交易后端保存订单事实，Spawn 后台通过管理适配读取；避免两边各维护一套可独立推进的订单状态机。
4. **多游戏隔离**：核查 Provider 装配、SKU、订单、回调密钥与存储实例的隔离。当前 teller 内部以 SKU/订单/Owner 建索引，不能仅凭网关 scope 就断言已经实现多厂商多游戏交易隔离。
5. **真实支付与发货**：渠道原生签名由对应服务端适配验证，再进入受信任支付链路；明确金额、币种、商户订单一致性。Courier 默认构造未注入 Deliver 时会将沙箱发货视作成功，生产必须接真实发货及幂等记录。
6. **管理面**：现有 Reconcile 是进程内方法；SKU 管理、补单、退款、全局订单查询、经营投影与结算需要受权限保护的管理适配，不能假定已有 HTTP 管理 API。
7. **冻结契约**：现下单体只有 skuId。角色绑定、活动报价、优惠券、退款等缺项先设计服务端关联与兼容扩展；必要时回 Courier 提案，不在 Spawn 旁路改造 SDK 协议。

建议交互关系：玩家在 Spawn 浏览、下载、参加活动；游戏内沿用 Courier SDK → Courier Gateway → 已选择的 Provider/服务。Spawn 的开发者与运营后台通过管理接口或事件接入公共能力。具体部署位置和适配代码归属在接入设计时确定，本调研不要求把 Courier 代码复制进 Spawn。

## 5. 活动模型建议

商品保存基础购买内容，活动保存额外赠送或优惠。以“支付 10 元，基础 100 游戏币，活动后总共 1000 游戏币”为例，基础发货 100、额外赠送 900；明确倍率指总量还是额外量，避免“十倍送”歧义。

活动最小结构：名称、状态、起止时间与时区、适用游戏/区服/渠道/人群、触发条件、奖励、限领次数、预算及叠加规则。订单/奖励记录保存命中的活动版本、基础内容、优惠金额、赠送明细和目标角色快照，后改活动不改变旧订单。

金额用最小货币单位整数记录，区分商品标价、实际支付、优惠金额、优惠承担方、赠送数量、可结算金额。赠币不是现金收入；厂商分成基数由合同配置，不按赠币倍率扩大流水。

活动资格与价格只在服务端计算；兑换、发奖和补发均需幂等。规则调整、退款后的奖励处理及超预算行为要可追踪；活动退场后不能丢失玩家已获权益的查询记录。

| M0 接入边界与基础治理 | 明确 Courier 复用、身份/目录/交易归属，补最小管理权限和存储方案 | 本文、两仓当前契约 | 有接口与数据映射、隔离用例、联合沙箱部署方案，无新建重复 SDK 任务 |
| M1 游戏发行与下载 | 联运标签、资料、合作方/运营入口、版本发布、Android 下载更新 | M0 身份/权限；发行授权与包体存储 | 同库混合浏览；标签可筛选；非联运条目仍正常；有权限的包可发布与下载更新 |
| M2 Courier 联调与交易 | 平台身份关联、角色目标、真实支付适配、发货补单、账单 | M0；一款合作/示例游戏；Provider 管理适配 | 沙箱完成全链路；正式收款另需真实渠道与游戏服验收，不以模拟成功替代 |
| M3 活动与玩家服务 | 礼包、倍率活动、首充/累充、券、开服提醒、工单 | M2 交易事件；部分非付费礼包可提前 | 规则可发布，奖励可查，重复事件不重复发放，优惠/退款可核对 |
| M4 增长与深化 | 游戏评价/预约/测试、经营分析、渠道归因、厂商结算增强 | 可信事件与管理权限；按需选取 | 指标口径、归因、账单与访问控制可复核；不承诺全部候选功能同时上线 |

跨仓联合验收最小旅程：开发者提交游戏 → 运营审核版本 → 玩家按标签找到并下载 → 游戏通过 Courier 登录 → 绑定区服角色 → 购买商品 → 服务端确认真实/沙箱支付 → 基础商品与活动奖励按订单幂等发放 → 玩家与后台查询一致 → 账单可核对。负向场景覆盖跨游戏/跨厂商越权、伪造回调、重复回调、发货失败、重启恢复及退款冲减。

## 7. 后续候选与外部依赖

账号交易、小号回收、平台储值币、会员付费、多级代理、自动打款、渠道 SDK 聚合及跨境/iOS 第三方分发仅记候选，未纳入首版。后续是否需要由真实接入需求决定，不将竞品宣传中的全量能力当成实施范围。

外部依赖包括游戏授权和素材、真实支付商户与测试凭据、游戏服发货/退款接口、包体存储和域名、Android 真机。实名防沉迷等能力按适用地区及实际服务接入记录验证；本文只记录产品与技术接入点，不将商业平台的资质说明当作完整法律结论。
